## 📊 프로젝트 워크로드 분석

귀하의 프로젝트는 **AI 기반 문서 자동 처리 시스템**으로, 다음 3단계로 구성됩니다:

### 1단계: OCR (PaddleOCR) - ⭐ CPU 집약적
- **CPU/GPU 병렬 처리** (멀티코어 활용도 매우 높음)
- vCPU 수가 처리 속도에 **직접적으로 비례**
- **매 문서마다 실행** (가장 빈번한 작업)
- 이미지 디코딩, 전처리, 후처리 모두 CPU 작업

### 2단계: 문서 분류 (DistilBERT) - 가벼운 파인튜닝
- 파라미터: 268M (BERT의 40% 크기)
- GPU 메모리: 학습시 2-4GB, 추론시 1-2GB
- 배치 크기: train=8, eval=16
- 에포크: 3회
- **학습 시간: 30-60분** (한 번만 실행, 이후 추론만 사용)
- ⚠️ **학습은 전체 워크플로우의 5-10%에 불과**

### 3단계: LLM 추출 (Qwen2.5:7b) - ⭐ 메모리 집약적
- 파라미터: 7B (가장 리소스 집약적)
- GPU 메모리: 4-5GB (양자화), 14GB (FP16)
- **시스템 RAM: 추가 4-8GB 필요** (컨텍스트 캐싱)
- CPU 모드시 180초 타임아웃 (GPU 필수)
- **매 문서마다 실행** (OCR만큼 빈번)

### 💡 핵심 인사이트

**학습 vs 추론 시간 비율:**
```
┌─────────────────────────────────────────┐
│ 1회 학습: 30-60분 (초기 1회만)           │
├─────────────────────────────────────────┤
│ 추론 (100개 문서): 30-50분               │
│ 추론 (1000개 문서): 5-8시간               │
│ 추론 (10000개 문서): 50-80시간            │
└─────────────────────────────────────────┘
```

**→ 프로덕션에서는 추론이 99% 이상의 시간을 차지!**  
**→ GPU 선택의 핵심은 "반복적인 OCR + LLM 추론"에 있음!**

## ⚡ 성능 영향 분석

### 1. GPU 메모리 요구량

```
동시 실행시 필요 VRAM:
├─ DistilBERT 학습: ~3GB
├─ Qwen2.5:7b 추론: ~5GB
└─ 시스템 오버헤드: ~2GB
───────────────────────────
총합: ~10GB

두 서버 모두 24GB VRAM → 충분 ✅
```

### 2. CPU/RAM 병목현상 (중요!)

#### ❌ g5.xlarge (4 vCPU, 16GB RAM)의 문제점:

- **OCR 병렬처리 제한**: 4개 코어로는 배치 처리시 대기시간 발생
- **메모리 부족 위험**: 
  - 모델 로딩: ~8GB
  - 데이터셋 캐싱: ~4-6GB
  - 시스템: ~2GB
  - **총 14-16GB → 16GB 한계 도달, 스왑 발생 가능**
- **데이터 로딩 지연**: CPU 코어 부족으로 I/O 대기

#### ✅ g5.2xlarge (8 vCPU, 32GB RAM)의 장점:

- **OCR 속도 2배**: 병렬 처리로 문서 수십~수백장 처리 가속
- **안정적 메모리**: 32GB → 여유 50%, OOM 위험 없음
- **배치 크기 확대 가능**: 더 큰 배치로 학습 효율 증가
- **멀티태스킹**: OCR과 전처리 동시 실행 가능

## 🎯 최종 추천: g5.2xlarge

### 핵심 이유 3가지

#### 1️⃣ 프로젝트 특성상 CPU가 병목점

- 귀하의 파이프라인은 **OCR → 전처리 → 모델 추론** 3단계
- GPU는 모델 추론(20-30%)만 사용, 나머지 70-80%는 CPU 작업
- vCPU 4개 → 8개는 **체감 성능 향상 2배 이상**

#### 2️⃣ 메모리 안정성 확보

- 16GB는 **한계 도달 위험** (실제 가용 메모리 14GB)
- 32GB는 **안전한 여유** (스왑 없음, 안정적 처리)
- OOM(Out of Memory) 에러로 작업 중단되면 **시간/비용 손실 큼**

#### 3️⃣ 실질적으로 더 저렴

- 시간당 20% 비싸지만, **작업 완료 시간 30-40% 단축**
- 시간을 돈으로 환산하면 g5.2xlarge가 경제적
- 해커톤처럼 **시간이 제한된 상황**에서는 필수

├─ [1000회] OCR:        1.1시간  (4초 × 1000, 50% ⬇️)
├─ [1000회] 분류 추론:  0.1시간  (0.5초 × 1000, 37% ⬇️)
├─ [1000회] LLM 추론:   2.2시간  (8초 × 1000, 33% ⬇️)
└─ Total:              3.6시간/일  (38% ⬇️)
   총 비용: 3.6시간 × $0.727 = $2.62/일 = $79/월
   
월간 절감: $26 (25% 저렴)
```

### 💡 핵심 결론

- **학습 영향도**: 전체 작업의 5-10% (한 번만 실행)
- **추론 영향도**: 전체 작업의 90-95% (반복 실행)
- **GPU 차이**: 두 서버 모두 동일 (24GB A10G)
- **결정적 요소**: CPU 코어 수와 시스템 RAM
  - g5.xlarge: 4코어, 16GB → 병목 발생
  - g5.2xlarge: 8코어, 32GB → 원활한 처리

## ❓ FAQ (자주 묻는 질문)

### Q1: "모델 학습이 30-60분이면 g5.xlarge로도 충분하지 않나요?"

**A:** 학습은 **전체 작업의 5%**에 불과합니다!

실제 작업 분해:
- **학습**: 30-60분 (초기 1회만)
- **추론**: 수백~수천 번 (매 문서마다)

예시:
```
1000개 문서 처리시:
- 학습: 50분 (한 번만)
- 추론: 5.8시간 (g5.xlarge) vs 3.6시간 (g5.2xlarge)
→ 학습은 전체의 12%만 차지
→ 추론 속도 개선이 훨씬 중요!
```

### Q2: "GPU가 같은데 왜 성능 차이가 나나요?"

**A:** 이 프로젝트는 **GPU보다 CPU/메모리가 병목**입니다!

리소스 사용률:
- **GPU**: 20-30% (추론시에만 사용, 나머지는 대기)
- **CPU**: 90-100% (OCR, 전처리 항상 실행)
- **RAM**: 80-90% (모델/데이터 캐싱)

vCPU 4개 vs 8개:
- OCR 병렬 처리 속도 **50% 차이**
- 데이터 로딩/전처리 **2배 빠름**

### Q3: "16GB RAM으로도 충분하지 않나요?"

**A:** 위험합니다! 메모리 요구량:

```
필요 메모리 (동시 실행):
├─ Qwen2.5:7b:        5-8GB
├─ DistilBERT:        2-3GB
├─ 데이터 캐싱:       3-5GB
├─ 시스템:            2-3GB

g5.2xlarge (32GB): 안전한 여유 ✅

OOM 발생시:
- 프로세스 중단 → 재시작 필요
- 스왑 사용 → 속도 10-50% 저하
- 디버깅 시간 낭비
